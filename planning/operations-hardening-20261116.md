# はりまよりみち｜止まらないための運用設計（2026-11-16）

## 目的・前提
- GitHub Actionsの定時実行は遅延・欠落することがある。毎朝08:25 JSTの主実行に加え、17:17 JSTの予備実行を設ける。
- **主実行が同一JST日に存在した場合**、予備枠はその成否に関係なくリクエストをせず終了する。実行履歴の取得に失敗した場合も予備取得しない。
- source_state.jsonの`attempt_day`および`attempts`による**1日1回**の上限は従来どおり有効。手動dispatchも同上限に従う。
- 1日1回のため、通信した後のエラーを当日自動再試行しない。翌日まで待つか人手で根拠と状態を確認する。

## 停止分離
- 情報源のライセンス・robots・スキーマ・URLの審査は静的ビルド時も保持する。
- 30日以内の人手再審査期限だけは**ネットワーク取得時**と**掲載可否判定時**に強制する。期限切れの場合、静的HTMLの生成を止めず、旧施設レコードを自動で掲載対象から外す。
- 最終確認日時を自動延長しない。審査期限切れを初回検出したらdata/source_state.jsonの`last_error`を1回だけ更新し、GitHubのデータコミット経由でCloudflare側に再生成を促す。
- 関連テストの不具合だけで実取得が毎日停止しないよう、取得ジョブでは安全機能に絞ったオフラインテストを使う。本番PR CIは全テストを維持する。
- 不正CSV、急減、取得権限変更、HTTP401/403/429、利用許可期限切れは**自動復旧させない**。強制push・権限迂回はしない。

## 監視
- 22:47 JSTと2つの定期ジョブ完了時に無料GitHub Actionsで診断。
- 最終成功が40時間超、当日の失敗、アクセス停止、審査期限の7日前から、GitHub Issuesに重複なしの要確認Issueを作成。
- 自動issueは通知メール送達まで保証するものではない。GitHubの通知設定を利用者側で確認すること。
- 原因調査と継続成功の確認後、Issueを手動で閉じる。次回異常時には新しいIssueを作る。

## 運用点検
1. [Actions](https://github.com/noranamani/noranamani-local-guide/actions)から各ジョブの実行時刻・conclusionを確認する。GitHubのcronは最大数時間遅延する可能性がある。
2. [source_state.json](../../data/source_state.json)で`attempt_day`、`attempts`、`last_success_at`、`halted`、`last_error`を確認。
3. [places.json](../../data/places.json)の日時を確認し、4件が不自然に消えたり重複したりしていないか確認。
4. Cloudflare Pagesの実際のデプロイとHTMLを確認する（GitHub側の成功だけでは公開反映を保証しない）。
5. 人手の再審査期限：2026-12-16より前。情報源の利用条件、robots、ライセンス、対象CSVを再確認してから審査記録を更新。

## 既知の限界
- 予備実行は二次的なcronであるため、GitHub自体の障害で**両方欠落**すれば自動復旧できない。
- 一度ネットワーク取得した日にrunnerが異常終了し、その状態をmainへ記録できない場合、別実行からリクエスト実施有無を完全保証することはできない。予備ゲートは同日先行runの存在を検知し、その条件で再取得を抑止する。
- GitHub Issuesの通知・Cloudflareへの実デプロイは別の監視対象。サイトの実HTMLやAPIへのアクセスが制限される環境では確認済みと表現しない。
